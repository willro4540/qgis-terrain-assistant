# 사례 연구 — 국토지리정보원(NGII) 실제 공공데이터로 좌표계 정제 실습

> 검증 상태: 이 문서의 모든 명령/결과는 실제로 실행해서 얻은 것(2026-09-02). 도엽번호→좌표
> 역산 부분만 근거 부족으로 미확정(아래 §4 참고).

이 저장소가 존재하는 이유(좌표계 정제 자동화)를 실제 국토지리정보원 공개 데이터로 검증한
기록. 파일은 `C:\Users\user\Downloads\`에 있고 용량이 커서(항공사진 1.1GB) 이 저장소에는
커밋하지 않음 — 재현 절차만 문서화.

## 1. 다운로드한 원본 파일

| 파일 | 종류 | 크기 |
|---|---|---|
| `(B010)수치지도_35616032_2000_...shp/.dbf/.shx/.xml` | 수치지도 1:2000, 단일 SHP | ~380KB |
| `(B010)수치지도_35616033_2025_...dxf` | 수치지도, DXF | 13MB |
| `(B010)수치지도_35616033_2025_...zip` | 수치지도Ver2.0, SHP 다수(N3A_*) | 2.7MB |
| `(B022)국가기본도20260902....zip` | 국가기본도, 중첩 zip 53개 레이어 | 685KB |
| `(B040)항공사진_...tif` + `.tif.irx` + 메타데이터 xml | 항공사진 25cm 해상도 | 1.1GB+944MB |

## 2. 좌표계(CRS) 문제 — 실제로 있었고, 실제로 고쳤음

`ogrinfo -al -so`로 확인한 결과:

| 파일 | 원래 상태 | 실제 CRS |
|---|---|---|
| 수치지도(SHP, 35616032) | `.prj` 없음 → "Layer SRS WKT: (unknown)" | **EPSG:5186** (등급 b, 아래 근거) |
| 수치지도(DXF) | DXF는 원래 CRS 필드가 없음(포맷 자체 한계) | 동일 지역이므로 EPSG:5186으로 추정(등급 c) |
| 수치지도Ver2.0(zip 안 N3A_*.shp) | `.prj` **있음** | `Korea_2000_Central_Belt_2010` = **EPSG:5186**(등급 a, 파일에 직접 명시) |
| 국가기본도(등고선/표고점/건물, zip 중첩) | `.prj` **있음** | `Korea 2000 / Unified CS` = **EPSG:5179**(등급 a) — 위와 **다른 좌표계**! |

**핵심 발견**: 같은 국토지리정보원이 배포한 데이터인데도 상품(수치지도 vs 국가기본도)에
따라 **서로 다른 좌표계(5186 vs 5179)**를 씀. 실제로 좌표값 자체도 완전히 다른 범위로
나타남(5186 계열은 X≈179,000~186,000, 5179 계열은 X≈935,000~936,000) — 같은 지역이라도
투영 원점이 다르면 숫자가 전혀 안 맞아 보임. **이게 바로 QGIS의 On-the-fly 재투영이
필요한 이유를 실제 데이터로 보여주는 사례.**

### 2-1. 실제로 고친 방법 (재현 가능)

`.prj`가 없던 수치지도(SHP)에, 이미 확보한 정확한 WKT를 그대로 파일로 써넣음:

```bash
cat > "(B010)수치지도_35616032_2000_73108867664621.prj" << 'EOF'
PROJCS["Korea_2000_Central_Belt_2010",GEOGCS["GCS_Korea 2000",DATUM["D_Korea_2000",SPHEROID["GRS_1980",6378137,298.257222101]],PRIMEM["Greenwich",0],UNIT["Degree",0.017453292519943295]],PROJECTION["Transverse_Mercator"],PARAMETER["latitude_of_origin",38],PARAMETER["central_meridian",127],PARAMETER["scale_factor",1],PARAMETER["false_easting",200000],PARAMETER["false_northing",600000],UNIT["Meter",1]]
EOF
```

**Before/After 검증** (`ogrinfo -al -so "(B010)수치지도_35616032_2000_73108867664621.shp"`):

- Before: `Layer SRS WKT: (unknown)`
- After: `Layer SRS WKT: PROJCRS["KGD2002 / Central Belt 2010", ...]` — GDAL이 EPSG:5186을
  실제로 인식함(내부 명칭이 "KGD2002"로 표시되는 것도 정상 — Korea_2000의 GDAL 별칭).

DXF는 포맷 자체에 CRS 필드가 없어서 파일을 못 고침 — QGIS에서 레이어 속성(Layer
Properties → CRS)으로 EPSG:5186을 수동 지정하거나, `ogr2ogr -a_srs EPSG:5186 out.gpkg
in.dxf`로 변환하면서 지정하는 게 정석.

**근거 등급이 (a)가 아니라 (b)/(c)인 이유**: 이 SHP/DXF 자체 폴더 안에는 원래 `.prj`가
없었음 — EPSG:5186이라는 결론은 (1) 같은 압축파일 안 다른 버전(Ver2.0)의 실제 `.prj`,
(2) 항공사진 메타데이터 XML의 투영 파라미터(중부원점/GRS80/TM/false easting,northing
200000,600000)가 **독립적으로 일치**한다는 정황 증거이지, 이 파일 자체에 새겨진 1차
증거는 아님.

## 3. 압축파일 한글 파일명 깨짐 — 원인은 파일 손상이 아니라 도구 문제

`unzip`(Git Bash)으로 열면 `(B022)국가기본도...zip` 내부 파일명이 깨져 보였지만, **실제
파일 자체는 멀쩡함** — PowerShell의 `Get-ChildItem`으로 확인하면 파일명도, `System.IO.
Compression.ZipFile`로 연 zip 내부 항목명도 전부 정상적으로 한글이 나옴. 원인은 Git Bash
환경의 로캘/`unzip`이 EUC-KR/CP949로 인코딩된 zip 항목명을 UTF-8로 잘못 해석한 것 —
**PowerShell + .NET의 기본 인코딩을 쓰면 문제 없음**.

실제로 열어보니 이 zip은 **중첩 zip 구조**(안에 또 zip 53개)이며, 국가기본도 표준 레이어
53종을 담고 있음: 건물/건물부속시설/건물중심점, 경지경계, 도엽인덱스(1000~250K 6종),
**등고선**, 면형/선형/점형 공항·구조·도로·철도·항만시설, 보도경계면/중심선, 수로시설,
행정구역경계(시군구/시도/읍면동), 실폭하천, 자전거도로중심선, 차도경계면/경계선/노드/
링크/중심선, 철도경계면/노드/링크/중심선, **표고점**, 표준유역계, 하천경계/경로/노드/링크/
중심선, 해안선, 호소.

**지형(terrain) 관련 핵심 레이어 실측 확인**(`등고선.zip`, `표고점.zip` 실제 추출·오픈):
- `등고선`(contour line): LineString, 68개 피처, EPSG:5179
- `표고점`(elevation point): Point, 92개 피처, EPSG:5179

즉 국토지리정보원 데이터만으로도 OpenTopography 없이 **국내 등고선/표고점 벡터 데이터를
직접 쓸 수 있음** — `qgis-terrain-assistant`의 데이터소스로 추가할 가치가 있는 대안(다음
세션 과제, 이 세션 범위 밖).

## 4. 항공사진(TIF) 지리참조 — 시도했으나 정밀 확정은 실패 (정직하게 기록)

`gdalinfo`로 확인: 모서리 좌표가 픽셀 좌표(0,0)~(14592,25728)뿐, 실세계 좌표 없음.
`TIFFTAG_SOFTWARE=Adobe Photoshop 21.1` — 포토샵을 거치며 지리참조 태그가 제거된 것으로
추정(등급 c).

메타데이터 XML의 `해당도엽번호150000=35616`을 국토지리정보원 공식 도엽번호 체계로 역산해
정확한 사진 모서리 좌표를 구하려고 조사했으나, **국내 도엽번호(35616 같은 5자리 숫자
체계)는 국제 표준 1:50,000 도엽 표기(예: NJ52-13:20)와 다른 국토지리정보원 자체 번호
체계**이고, 이번 세션에서 그 정확한 환산식/조견표를 확인하지 못함(등급 d, 열린 질문).

**대신 확인된 것**: 같은 도엽번호(35616)를 파일명에 쓰는 수치지도 파일들(`35616032`,
`35616033`)이 이미 있고, 그 SHP 파일들의 실제 좌표 범위(EPSG:5186 기준 X:179,236~186,566
근방)가 이 항공사진과 같은 지역(행정구역명=광주광역시 동구 광산동 부근)을 가리킨다는
정황은 확인됨 — 이걸 **근사 경계 상자로 참고**할 수는 있지만, 정확한 지리참조(정밀
`gdal_translate -a_ullr`)를 이 근거만으로 단행하는 건 근거 등급 (d) 상태를 (a)처럼 쓰는
것이라 하지 않음. 정확한 위치 확정은 다음 중 하나가 필요: (1) 국토지리정보원의 공식
도엽번호-좌표 변환표, (2) 같은 지역의 이미 지리참조된 위성/항공영상과의 지상기준점(GCP)
수동 매칭(QGIS Georeferencer 도구), (3) 국토지리정보원에 직접 문의.

## 5. 속성 데이터 실제 내용

수치지도(35616032) SHP의 실제 피처 1건 예시:

```
UEE (String) = 2920010600
UEC (String) = 2920056500
PNU (String) = 104440000
UAA (String) = 015
ARA (Integer) = 0
UCA (String) = 922
STM (String) = 1000
```

**주의**: `PNU` 필드명이 한국 표준 필지고유번호(19자리)를 연상시키지만, 실제 값은 9자리뿐
(`104440000`)이라 **표준 19자리 PNU 형식과 다름**(등급 c — 이 필드가 실제로 뭘 의미하는지는
국토지리정보원의 수치지형도 속성코드 규격 문서를 봐야 확정 가능, 이번 세션엔 미확인).

## 6. QGIS 프로젝트 파일 — 만들지 않음 (정직한 스코프 결정)

`.qgs`/`.qgz`를 이 세션에서 직접 생성하는 대신, 사용자가 QGIS에서 직접 여는 걸 권장 —
`.qgs` XML을 라이브 QGIS 검증 없이 손으로 작성하면 미묘한 스키마 오류로 파일이 안 열릴
위험이 있어서, 확실하지 않은 걸 "만들었다"고 하지 않음([[research-verification]] 원칙).
대신 정확한 파일 경로와 확정된 CRS를 위에 전부 남겨서, QGIS에서 "레이어 추가"로 바로 열 수
있게 함.

## 7. 다음에 이어서 할 일

  지리참조 완료.
- `등고선`/`표고점` 레이어를 `qgis-terrain-assistant`의 새 국내 데이터소스로 추가 검토.
- `PNU`류 필드의 정확한 의미를 국토지리정보원 수치지형도 속성코드 규격에서 확인.
